# Kubernetes Node Roles

---

[DOC OFFICIELLE](https://kubernetes.io/fr/docs/concepts/architecture/nodes/#gestion) et [VIDZ](https://www.youtube.com/watch?v=sKv601iCwjY)

## Description de la composition d'un `Node` : 

Un `node` peut être une machine virtuelle ou physique, selon le cluster, il fournit le hardware pour faire tourner `k8s`.

Sur chaque `node` tournent obligatoirement trois composants :
- `kubelet` : agent local, il démarre et surveille les pods que l'api-server lui assigne
- `kube-proxy` : programme les règles réseau (iptables/IPVS) qui font fonctionner les Services
- un `container runtime` : `containerd` ou `CRI-O`, c'est lui qui lance réellement les conteneurs

---

### - `Pod`:
- Plus petite unité **déployable** de `Kubernetes`. Contient un ou plusieurs conteneurs qui partagent la même IP, les mêmes volumes et le même namespace réseau.
- Il est planifié sur un `node` par le `scheduler`, puis démarré et surveillé localement par le `kubelet`.
- Un `pod` est **éphémère** : son IP change à chaque recréation. C'est la raison d'être du `Service`.

---


### - `Control plane` :
- Orchestrateur du cluster : il définit l'état souhaité et le maintient. Anciennement appelé `master`.
- Composants :
  - `kube-apiserver` : point d'entrée unique, seul composant à parler à `etcd`
  - `etcd` : base clé/valeur, stocke tout l'état du cluster
  - `kube-scheduler` : choisit sur quel `node` placer chaque nouveau `pod`
  - `kube-controller-manager` : boucles de réconciliation (état réel → état souhaité)
- Le control plane tourne lui-même sur un ou plusieurs `nodes`. Un node control plane porte le taint `node-role.kubernetes.io/control-plane:NoSchedule`, qui empêche par défaut le scheduling de pods applicatifs. Retirer ce taint le transforme aussi en worker (cas du cluster single-node).

---



### - `Namespace` :
- Est une cloison logique dans un cluster, ils servent à : `Isoler`, `eviter les colision de nom` (Le nom est unique par namespace, pas par cluster.), `RBAC` (Droits), `Quotas de ressources`
- **Ne fait PAS d'isolation réseau** : par défaut un pod du ns `dev` peut joindre un pod du ns `prod`. Il faut une `NetworkPolicy` pour cloisonner.
- Ressources non-namespacées : `Node`, `PersistentVolume`, `ClusterRole`, `StorageClass`, `Namespace`. Vérification : `kubectl api-resources --namespaced=false`


### - `Service ` :
### - `Service` :
- Expose un groupe de `pods` derrière une **IP virtuelle stable** + un nom DNS. Comme les `pods` changent d'IP à chaque recréation, le `Service` fournit le point d'accès fixe et répartit les requêtes.
- La sélection des pods cibles se fait par `selector` sur les **labels**, jamais par IP.
- Répartition de charge **L4** (TCP/UDP), implémentée par `kube-proxy` via iptables ou IPVS. Ce n'est pas un reverse proxy HTTP — ça, c'est l'`Ingress`.
- 4 types (`spec.type`) :
  - `ClusterIP` : défaut, joignable uniquement depuis l'intérieur du cluster
  - `NodePort` : ouvre un port (30000-32767) sur **chaque** node
  - `LoadBalancer` : demande un LB externe au cloud provider
  - `ExternalName` : simple alias DNS (CNAME), ne proxifie rien
- Cumulatifs : `LoadBalancer` crée un `NodePort`, qui crée un `ClusterIP`.
- Résolution DNS : `<service>.<namespace>.svc.cluster.local`

---

### - `Ingress` :
- Porte d'entrée **L7** (HTTP/HTTPS uniquement) : route le trafic externe vers les `Services` selon le `host` et le `path`, et gère la terminaison TLS.
- Point clé : une ressource `Ingress` seule ne fait **rien**. Il faut un `Ingress Controller` (nginx, traefik, HAProxy) déployé dans le cluster pour qu'elle soit appliquée.
- Pour du non-HTTP (TCP/UDP brut), l'`Ingress` ne convient pas : il faut un `Service` de type `NodePort`/`LoadBalancer`.
