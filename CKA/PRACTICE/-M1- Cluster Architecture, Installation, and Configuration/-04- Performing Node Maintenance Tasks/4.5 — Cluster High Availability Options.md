## High Availability 

---

`[NOTE]`

- Dans `kubernetes` la `H.A` est utilisé en cas de chute du node `controle plane`, en effet si ce node tombe, impossible de manager le cluster .

- Plusieurs options sont possible pour implémenter de la `H.A`:
   
   - -1- `Stacked control plane nodes` => Plusieurs controle plane nodes `mutualise etcd`

   - -2- External etcd cluster => `Etcd` est séparé par cotrole plane node.

- Dans cette configuration actuelle, `keepalived` fourni un `VIP`(Virtual IP) aux `control plane`, et `HA proxy` fait le `load balancer`.

- `Haproxy` fait tourner les requêtes entre chaque Master, et `keepalived` maintient un `VIP`.

- Si un node tombe `keepalived` bascule juste la VIP vers un autre — et `HAProxy` continue de router vers les masters restants encore up.
 
### **=== Pour l'examen ===**
````
`[NOTE]`

Version examen (join d'un `control plane` sur un cluster déjà en HA)

* Le cluster a déjà été initialisé avec `--control-plane-endpoint` (VIP / load balancer en place).
* Le nouveau node a déjà `containerd`, `kubeadm`, `kubelet` et `kubectl` installés, à la même version que le cluster.
* Doc officielle à chercher : `Creating Highly Available Clusters with kubeadm`.

`-1-` Sur un `control plane` existant : générer la `certificate-key` (valable 2 h)

````
sudo kubeadm init phase upload-certs --upload-certs
````

`-2-` Sur un `control plane` existant : afficher la commande de join

````
sudo kubeadm token create --print-join-command
````

`-3-` Sur le nouveau node : joindre en `control plane`

````
sudo kubeadm join <VIP>:6443 --token <TOKEN> \
  --discovery-token-ca-cert-hash sha256:<HASH> \
  --control-plane --certificate-key <CERT_KEY>
````

`-4-` Vérifier (depuis un `control plane`)

````
kubectl get nodes
````

* Le nouveau node apparaît avec le rôle `control-plane` et le statut `Ready`.
````
