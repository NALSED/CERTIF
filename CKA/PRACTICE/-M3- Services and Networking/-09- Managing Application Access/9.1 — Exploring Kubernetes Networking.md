# **Les Acteurs du réseaux Kubernetes**

## **Externe au Cluster**
- DNS         => résout le hostname vers l'IP du LB. Déclaration `A` `AAA` du service chez un provider ou on-promise.

- LB          => Répartit vers n'importe quel nœud sur le port NodePort. Chez un provider ou on-promise.


## **Interne au Cluster**

### === Implémentation (pods/DaemonSet) ===

- **CNI** :
   - Pods déployé sur chaque `nodes` utilisation d'un plugin (ici calico), gére le réseau des pods, sur `L2` et `L3`.

   - Il donne une `IP réél` à chaque `pods` / assure la connectivité physique.

---

- **kube-proxy** :

   -  S'appuie sur le réseau du CNI pour écrire ses règles de NAT (iptables/IPVS).

   - La rédirection de paquets est ensuite géré par le noyau Linux.

 ---

### === Objet Kubernetes (déclaratif) ===

- **Service** :

`[NOTE]`

- Les services ne fonctionnes pas seul ils sont imbriqués les un dans les autres pour pouvoir faire entrer /sortir du cluster

   - **ClusterIP**   => IP virtuelle interne, répartit vers les Pods (Actif par defaut)

   - **NodePort** =>  port ouvert sur CHAQUE nœud, redirige vers le ClusterIP

   - **LoadBalancer** => Demande un LoadBalancer chez le provider cloud OU à implémenter si le Load Balancer est On-Promise (Ne pas confondre l'objet Kubernetes et l'application qui fait le load balancing.)
 
   - **ExternalName** => Un alias DNS (CNAME) vers un nom externe, ex: une base de données hors cluster

---

- **Ingress**     => route HTTP/HTTPS selon le hostname ou le path vers le bon ClusterIP

- Utilise un `Ingress Controler` (Application tierce : nginx, Traefik, HAProxy...) : l'objet `Ingress` agis comme un `reverse proxy L7`, depuis les port `80 / 443` pour atteindre un service.

- Possibilité d'implémenté ces certificats `SSL`
